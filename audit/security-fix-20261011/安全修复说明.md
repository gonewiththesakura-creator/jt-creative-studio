# JT 工作台安全修复与上线验证

日期：2026-10-11。范围：个人上传凭据、账号隔离、管理权限及承载工作台的主机权限。

## 已上线

上传改为浏览器 → JT 服务器 → 云端。长期 API Key 只由服务端私密环境配置加载，不发给浏览器。图片/视频继续复用分片上传、断点续传和已完成上传结果。实测一张 68 字节的合成 PNG 经正式账号、正式 HTTPS 分片接口和云端上传成功；未调用任何生成接口。

| 原风险 | 修复及实际作用 |
| --- | --- |
| 旧网页保留直传 Key 输入及存储读取代码 | 删除该实现和签名依赖；登录初始化前定向删除本来源 localStorage/sessionStorage 的旧 Key 项及账号前缀变体，不读出、不发送其中值。外观和预设保留。 |
| 同一浏览器换账号后可能命中前一账号的媒体缓存 | 会员 API、媒体使用 no-store 与 Cookie 分区；身份检查、登录和退出清旧缓存。真实 Chromium 的 Alice → Bob 缓存复现已由 200 泄露变为 404。 |
| 自己置顶任务会修改其他用户队列 | 仅交换本人占有的位置，其他账号任务顺序与版本号不变，包括历史同序号任务。 |
| 登录回跳控制字符可跳向外站 | 严格允许工作台页面，拒绝控制字符、嵌套编码、非法地址；旧登录状态也重新验证。正式站异常回跳请求返回 400。 |
| 管理员激活码等同完整后台权限 | 日常使用仍为激活码登录。全部用户/套餐后台读取与修改必须经过独立的管理员身份登录，验证有效 15 分钟。代码会话访问后台返回 403；真实管理员身份验证后正常。此措施不宣称为 MFA。 |
| 上游重定向可能携带认证信息 | 带凭据的请求不跟随重定向；收藏下载只允许经校验的公网 HTTPS，每一跳固定解析地址，有大小、时长、低速和媒体签名限制。 |
| 一位用户占满媒体传输槽 | 每账号至多两个，全站四个大响应槽；离线并发验证另一账号仍能读取。 |
| 旧页面、过时脚本能被直接访问 | 会员模式只公开当前清单及精确必要入口，73 个资源逐项线上字节比对通过。旧页面及旧直传脚本返回 404。构建检查阻止供应商品牌/域名再次进入公开代码。 |
| 网站服务使用可免密码 sudo 的维护账号 | 改成独立 jt-panel 系统账号，无 sudo、无 Linux capabilities、禁止提权；运行代码与系统目录只读，仅数据目录和私有临时目录可写。线上检查有效。 |
| 服务单元中存在明文旧面板 Token | 移入 root 私有 0600 环境文件并轮换；会话签名使用独立随机秘密。实际云端 Key 并未因此轮换。 |
| 主机密码登录暴露 | 核实仅有 admin/root 两个交互维护账号后，改成 SSH 密钥认证，保留已有密钥和反向隧道能力，实测全新 SSH 连接成功。未调整同机其他业务的监听和防火墙。 |
| 激活码模式仍留公开注册入口 | 关闭身份服务的 JT 应用公开注册，原有管理员身份登录保留。 |

## 数据、权限与验证

- 上线前在服务器本地备份 SQLite、任务、收藏和上传凭据；没有上传本机账本覆盖生产。
- 原有 **995 条任务、46 条收藏**保留，用户、套餐、权益、激活码和额度记录核对一致。
- 未取消或重新提交任务，没有付费生成；上传验证只新增一个可自然过期的合成测试素材凭据。
- 服务账号切换后的正式登录检查发现 SQLite WAL/SHM 文件会继承数据库原所有者。已把该数据库及其侧文件的所有者与服务账号对齐；数据内容未替换。再次登录、后台验证、收藏分段读取均通过。
- 联合安全/认证/媒体/前端测试 **243 项通过**；队列/上传/发布保护另 **113 项通过**。前端专项检查包括真实 Chromium 假密钥清理、上传重试和管理员验证 UI。
- 正式网页在专用浏览器会话中打开，登录界面正常、没有浏览器异常；该检查会话已关闭。
- 343 个服务文件/日志对象和最近 3000 行服务日志中的当前秘密精确值及 Base64 扫描未发现命中。这不能证明历史上从未泄露。

## 仍需注意

1. **上游旧 API Key 尚未作废或轮换。** 新 HTTPS 来源无权清理旧 HTTP/端口来源的浏览器存储，也无法撤销已复制的值。需要在上游账号后台轮换 Key，再仅更新服务器私密配置。不要把新值贴进公开页面或聊天。
2. 这是对已确认边界的修复和验证，不是绝对防破解/防入侵保证。合法登录用户可保存自己有权查看的内容；限速与并发控制不能等同抗大规模 DDoS。云服务商安全组和独立 WAF 本次未改动。
3. 密码登录 SSH 已关闭，以现有维护密钥连接。管理员后台需要原先交付的管理员身份登录；普通用户仍只用激活码。
4. 长期 Key 留在后端有助于保密，但素材会经过服务器，消耗服务器带宽。真正由浏览器直传且不暴露长期 Key，需要上游支持短期、限定权限的签名上传凭证；本次没有假设或引入未验证的接口。

## 维护和回滚边界

生产加固备份仅保存在服务器 root 私有 `/var/lib/jt-security-hardening-20261011`；代码发布备份由原发布事务保存。加固脚本默认拒绝覆盖已有准备状态，不可不检查就再次执行 prepare/apply。回滚需要先停接新请求、等待已有任务自然结束，再由维护密钥连接执行已核验的恢复步骤；不能恢复旧数据库覆盖后来产生的用户数据。

关闭公开注册是独立且保留的安全设置，不会随代码自动回滚恢复。应用数据库仅新增可向后兼容的管理员会话验证表，旧账号与权益结构未改变。维护工具的队列只读检查已改为 sudo 读取，以兼容新的私有数据文件所有者。
