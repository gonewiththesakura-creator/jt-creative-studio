# JT 创作台：账号、套餐与安全运营手册

本手册对应 2026-10-10 的长期激活码登录版本。文档描述操作方法；某台服务器是否已完成切换，以该次发布记录和实际 HTTPS 验证结果为准。顾客不再注册用户名或密码，使用管理员发放的长期登录激活码进入自己的账号。

## 访问地址与管理员首次使用

| 用途 | 地址或入口 |
| --- | --- |
| 用户工作台 | `https://studio.dreamapi.club/` |
| 工作台管理员登录 | 工作台登录页「工作台管理员登录」，使用 `owner` 账号；验证后自动进入套餐设置 |
| 套餐、激活码、用户与额度管理 | 登录工作台后，右上角固定的「管理后台」；套餐的功能开关在「套餐设置」 |
| 用户套餐与兑换 | 工作台右上角账号名称 →「我的账号」 |

新工作台地址不带端口。原有 `dreamapi.club` 的其他 API 业务与新的工作台子域名分开；推广时使用完整的 HTTPS 工作台地址。登录域名会在浏览器跳转、网络请求和证书中公开可见，不能把域名视为秘密。

日常运营只需使用工作台的「管理后台」，包括套餐设置、登录激活码、续费码、用户与额度核对。管理员验证有效期为 15 分钟；过期后管理入口仍显示，点击后在面板内提示使用 `owner` 验证，完成后自动回到原来的管理页签。此时「我的账号」用于查看自己的套餐，不是管理其他用户的入口。

身份系统的 `admin` 是独立的维护账号，只用于身份、密码和登录设置维护，不是套餐后台，不用于日常发码；维护入口为 `https://auth.dreamapi.club/login/built-in`。普通身份账号在长期激活码模式下不能通过工作台管理员入口获得工作台会话。随机初始凭据通过私密文件交付，使用密码的管理员首次登录后应修改为各不相同的强密码。不要把交付文件发到群聊、上传 Git，或把其中内容粘贴到工单、截图和日志。

工作台管理员绑定的是已核验的 OIDC `issuer + subject`。仅注册同名用户名、显示名或邮箱，不会获得工作台管理员权限。原站主身份和旧数据迁移只能由服务器本机 CLI 完成，没有公开 HTTP 初始化管理员接口。

## 用户开通流程

1. 用户线下付款后，管理员核对实际收款与订单，从「管理后台 → 登录激活码」发放对应套餐的完整登录激活码。
2. 用户打开工作台，在「登录激活码」输入框粘贴该码，点击「进入创作台」，无需注册用户名或密码。
3. 首次成功登录会建立一个普通用户账号并开通发码时约定的套餐，有效期从首次登录时起算。发码后尚未登录，不会提前消耗套餐天数。
4. 以后在同一台或其他电脑继续使用同一个登录激活码，进入同一个用户账号，套餐、历史和收藏沿用，不会因为重复登录重新发额度。套餐到期后仍可登录查看自己的记录，但生成受套餐和额度限制。
5. 使用完共享电脑后点击「退出登录」。更换账号时页面会重新加载，提示词预设、待提交标识等浏览器数据也按用户 ID 分开存放。

登录激活码本身就是账号凭证，应像密码一样保管。把同一个码交给不同的人，会让他们进入同一个账号并共享其中数据和额度；需要相互隔离的用户必须分发不同的码。登录码不能绑定真实自然人身份，也不承诺禁止账号分享。

用户只能访问自己归属的任务、素材、历史、收藏和结果下载。浏览器页面隐藏不是权限依据，实际权限由服务端会话、归属校验和套餐账本决定。到期不会删掉已有记录，但已有媒体能否继续播放，还受文件保留及原结果可用性影响，不能将登录保留理解为永久素材存储承诺。

登录门禁先显示黑洞背景；用户完成登录后，登录窗口淡出，黑洞放大、淡出，再随工作台渐显成为常驻背景。普通已登录刷新不会重复播放这段进入动画。浏览器仅保存一个短期、非秘密的动画时间标记，不能凭它绕过登录；系统启用「减少动态效果」或用户已保存暂停光场、速度为零、透明度为零时跳过缩放，背景保留已保存的透明度，WebGL 不可用时保留纯黑背景。登录前不会挂载私有任务页面。

## 管理员：设置套餐、收款与发码

进入「管理后台 → 套餐设置」，选择「新建套餐」，填写名称、有效天数、图片额度、视频额度、允许同时运行的任务数、视频排队数、开放功能和生成方式，保存后即可发码。

「价格说明」只是管理员填写的销售说明，不会发起线上扣款。当前购买流程是线下收款、人工确认、发激活码。管理员应保留订单与发码备注的对应关系，避免只根据付款截图发码。

管理后台的两类码用途不同，不能混用：

| 类别 | 后台入口 | 用户使用方式 | 重复使用的结果 |
| --- | --- | --- | --- |
| 长期登录激活码，前缀 `JT-A-` | 「登录激活码」 | 未登录时输入，直接进入账号 | 重复登录原账号，不增加额度或延期 |
| 一次性套餐续费码，前缀 `JT-` | 「续费码」 | 登录原账号后，在「我的账号 → 兑换套餐续费码」输入 | 只可兑换一次，不可用于登录 |

在相应入口选择已启用的套餐，填写数量及订单备注，再生成。每次最多生成 100 个。完整码只在本次成功响应中显示；立即复制，保存到受控的交付记录，再分别交给买家。关闭管理面板后会清除本次明文码显示；服务端只保存哈希和尾号，不能从历史列表找回完整码。备注只记录订单编号等核对信息，不要把完整登录码写进备注。

长期登录码可以在首次使用前或使用后「作废」。作废立即阻止此码登录，并撤销该账号的现有会话，账号、套餐和历史本身不删除。要让原用户重新使用，应从「用户 → 更换登录码」补发，不能另发一个新用户登录码冒充恢复原账号。

一次性续费码仍按原规则：未兑换的可以「作废」，已兑换的不能再作废。重发前先核对状态，防止同一订单获得两份权益。历史列表有分页；已使用记录显示用户 ID 前缀，可与「用户」列表核对。发码请求超时后先刷新列表并核对订单记录，不要直接反复发码；响应未收到的完整码无法重新读取，需要确认并作废对应记录后重新交付。

修改套餐仅影响之后发出的激活码。每个激活码保存发码时的套餐快照，已发出的码及已开通权益不会随套餐编辑变化。停用套餐会停止继续为该套餐发码，不会撤销已发码或已开通权益。

原站主有一个仅用于内部管理的初始化权益：3650 天、图片和视频各 1000000 单位、并发 2、全部功能与生成方式。初始化兑换后，该套餐在套餐目录中停用，不作为默认销售套餐，不预设面向顾客的价格。正常运营请新建自己的销售套餐。

## 额度、并发与续费规则

图片按提交请求中的 `batch` 预占额度，例如一次提交 4 张，预占 4 个图片单位；视频按任务计，每个视频任务预占 1 个视频单位。任务成功后结算为已消耗，确认失败或确认取消且未产出后退回额度。同一任务的重复结算不会重复扣费或退款。

网络断开、提交状态不明、任务仍在云端运行等情形，不能直接认定失败，因此可能继续占用额度，待恢复查询或管理员核对结果。页面「剩余额度」是可继续提交的额度，已预占部分不计入可用余额。

套餐并发是该账号的上限，同时还受平台全局并发约束；当前云端任务全局上限是 **2**。两个账号都购买「并发 2」，不表示全站可同时运行 4 个云端任务，也不代表独享两张显卡。超出当前可用并发的任务继续排队。套餐设置与销售说明应明确这一点。

「视频排队数」可设为 1–100，按账号计算等待中的视频，不包括正在生成的视频，也不包括图片任务。例如并发 2、视频排队数 10，表示该账号最多同时运行 2 个任务、另外等待 10 个视频；实际执行仍受全站可用并发限制。排队已满时服务端拒绝新增视频，不扣额度；已有任务开始执行或取消排队并完成状态更新后可以继续提交。全站等待队列仍有总容量限制。

旧套餐和已有激活码、权益中没有排队设置的，按原有上限 100 兼容，不清理现有排队任务。编辑排队数与其他套餐权限一样，只影响之后新发出的激活码，已发码和已开通权益保留当时的配置；用户可在「我的账号」查看自己的视频排队上限。

续费时，用户先用原长期登录码进入原账号，管理员线下核款后发放一次性续费码，用户在「我的账号 → 兑换套餐续费码」兑换。续费不会更换账号或登录码；不要把新顾客使用的长期登录码当成续费码。网络中断时先点「刷新套餐」核对结果，再决定是否重新兑换。

有效套餐期间，兑换同一个套餐且功能范围、生成方式、并发设置、视频排队数相同的续费码，可以累加图片/视频额度，并在原到期时间上追加有效天数。有效期内不能兑换不同套餐，也不能用改变上述权限的同套餐续费码直接升级；应在到期后开通其他套餐，或由维护人员另行处理有记录的变更。已过期后兑换会建立新权益，旧套餐剩余额度不会自动并入新套餐。

## 管理员：核对长期未结算额度

进入「管理后台 → 额度核对」，点击「刷新待核对列表」，查看任务编号、所属用户、所占单位和原因。此页面只读取本地账本，打开列表和结算都不会重新提交付费生成任务。

对允许处理的记录，先在实际生成服务中核实结果，再选择：

- **确认计费**：已核实确实产出结果，将占用额度结算为已消耗。
- **退回额度**：已核实没有产出结果，将占用额度退回用户。

两种操作都要填写至少 10 字、最多 500 字的核对依据，并在确认框中再次确认。建议记录核对时间、实际结果与判断依据。操作会记录管理员、任务、结算方向和说明。

进行中、排队中、恢复查询中或仍有占位保护的任务不能人工处理。不要仅凭「等了很久」退款，也不要为了清空列表改写任务状态。若按钮不可用，先处理任务的真实运行状态。结算状态已发生变化时，服务端会拒绝冲突操作；刷新列表后重新核对。

## 停用、恢复、丢码补发与管理员 MFA

「管理后台 → 用户」可以停用或恢复普通用户。停用会阻止继续使用、撤销工作台全部会话，并永久作废当时有效的长期登录码。恢复账号不会让旧码重新生效：先恢复账号，再执行「更换登录码」，将新码私密交付给已核实的原用户。套餐期限和余额不会因为停用、恢复或换码自动延长、重置。

用户丢失登录码时，管理员先核对订单、原付款渠道和既有交付记录，确认正确用户 ID 后，在该用户记录上执行「更换登录码」。只凭昵称、尾号或聊天自述不足以证明账号归属。新码仍对应原用户 ID 和原数据归属，原套餐、历史、收藏和额度保持；旧码和全部旧会话立即失效。新码只显示这一次，若未保存就关闭，需要再次换码；不要另建账号或从备份恢复旧明文凭据。

停用或换码不等于取消已经提交到生成服务的任务，处置前应核对是否仍有运行中的任务。怀疑码泄露时应及时换码并核对异常任务；持码人已下载的数据无法通过换码收回。

普通顾客没有用户名密码找回步骤，也没有自动邮件找回长期码。管理员身份系统目前尚未配置 SMTP，不能承诺邮件自动找回管理员密码；需要在核验身份后由受信任维护人员处理。使用身份服务登录的管理员应启用其验证器 MFA 并妥善保管恢复信息。此 MFA 不适用于顾客长期码登录，也不代表全站强制双因素验证。

## 安全措施及实际边界

生成服务和模型 API 的密钥只保存在服务器环境中。会员上传走工作台受鉴权的分块接口，页面不再要求用户填写平台共用 Key。API 响应、公开健康检查和前端日志不应展示生成服务地址、共享密钥或身份应用密钥。

长期登录码由 192 位随机值生成，数据库保存 SHA-256 哈希和显示尾号。输入可忽略空白与大小写，但必须符合完整固定格式；原一次性兑换码不会自动变成登录凭证。顾客登录只接受本站来源的 JSON POST，不从 URL 接收登录码；校验成功后另发 HttpOnly/Secure 会话 Cookie，登录码不作为会话 Cookie 保存。校验码到创建会话之间会再次在事务中验证凭证仍有效，避免换码与登录并发时恢复旧会话。应用不把登录码写入浏览器本地存储；浏览器或密码管理器自身是否保存，由用户选择。

其他防护包括 HTTPS、管理员身份登录的状态/PKCE/nonce 与签名验证、同源和 CSRF 校验、逐用户数据归属、服务端套餐与额度校验、管理员权限校验、CSP、访问速率限制及反向代理入口限制。业务脚本只允许本站来源，不开放脚本 `unsafe-eval` 或 `unsafe-inline`；为现有界面保留的是样式内联能力。

这些措施降低撞库、跨站请求、越权下载、激活码枚举和资源滥用风险，但不能保证「绝对防爬」「绝对防破解」或「永不被入侵」。静态前端代码本来就会发送到用户浏览器，不应把隐藏按钮或压缩 JavaScript 当成安全边界；已授权用户也可能复制自己能看到的内容。大流量攻击仍需结合云防火墙、带宽防护、监控告警和及时更新依赖处理。

长期码登录按入口 IP 限制为每 10 分钟最多 20 次尝试，成功与失败都计数；同一出口网络的多名用户可能共用该限制。出现大量 429 时先核对集中使用或异常访问，不要直接关闭限流。身份服务的验证码、登录错误限制和应用版本仍应随升级检查。备份、运维 SSH 和管理员凭据应与普通用户账号分离管理。

应用源码包括 `membership_auth.py`、`membership_http.py`、`membership_store.py`、`membership_media.py`、`server.py`。前端修改后按既有构建流程运行相关页面构建器，再运行 `tools/build_frontend.py`；发布 `static/app.html`、`static/app-manifest.json` 及清单引用的全部哈希资源，不能只上传某一个业务 JS 文件。

长期码登录模式由 `JT_MEMBERSHIP_ENABLED=1` 与 `JT_LOGIN_MODE=access_code` 启用；管理员 OIDC 配置继续保留。服务器当前模式可从匿名 `/api/auth/me` 的 `login_method` 核对，不能仅凭前端输入框判断切换成功。

发布前验证：不同码产生隔离账户，同一码在两个浏览器回到相同用户；并发首登只开通一次额度；到期可登录但不可无套餐生成；换码和停用撤销旧码及会话；顾客不能通过管理员 OIDC 入口绕过码登录；续费码不能重复兑换或用来登录；缺失来源或 CSRF、伪造身份和跨账户请求被拒绝。套餐/并发/额度必须在服务端校验，账号切换清除旧页面状态，上传和结果读取走本站授权接口。可用离线固定样例验证，不需要为演示重提交付费生成任务。部署后还要核对实际 TLS、Cookie、服务绑定地址及公开端口，不能仅凭单元测试判断已完成安全上线。

## 备份、原站主迁移与回滚

升级前从**生产服务器当前数据**建立同一时间点的备份，至少共同保存会员 SQLite、任务/收藏/上传凭据账本和实际素材/收藏文件。SQLite 运行时应使用 SQLite 在线备份或在服务停止后备份数据库及 WAL/SHM；不要在运行时只复制主数据库文件。身份服务数据库和机密配置另行备份，并限制备份文件读取权限。

`tools/migrate_membership_owner.py` 默认只读，输出三类账本的记录数量。执行 `--apply` 时要求 `comfy-panel.service` 为 `inactive`，核对 `PANEL_DIR` 与服务配置一致，并使用已封存核验的 `JT_OIDC_ISSUER` 和 `--subject` 指定原站主，不能通过邮箱抢占管理员。

迁移先备份服务器现有三个账本及会员数据库，再在副本中创建站主权益、调整归属，最后原子替换。它不会修改原任务状态、队列顺序、提示词、素材路径，也不会创建生成额度占用或向生成服务重新提交任务。提交失败会恢复备份；提交中断的阶段记录可供下一次离线执行先恢复再继续。成功标记使重复执行不再叠加额度。

回滚前先暂停公开写入、等待或安全处理当前任务，再停止服务。使用本次发布记录中的代码/配置备份，先确认其兼容当前会员数据库。不要直接把已产生新用户、新订单或新任务之后的数据回滚到上线前，否则会丢失真实权益与账本。

长期登录码版本把会员库升级至 schema v2，新增独立 `login_credentials` 表，不把旧兑换码改造成登录码。旧 schema v1 的存储代码会拒绝读取 v2；回滚业务界面或 HTTP 代码时须保留兼容 v2 的存储代码，或另行制定数据迁移方案。不能为了让旧代码启动而手工降低 `user_version` 或删除登录凭证表。

若必须恢复数据，要共同核对任务账本和会员数据库的同一备份时间点，并保留恢复前当前生产数据。原站主迁移备份是迁移时的快照，不是可任意覆盖后续运营数据的日常恢复点。不得用开发机账本覆盖生产。

如果回退到不支持会员鉴权的旧代码，必须先关闭公开入口或展示维护页；不能只把 `JT_MEMBERSHIP_ENABLED` 关闭后继续对外开放。恢复服务后再次验证登录、用户隔离和额度，再解除维护状态。
